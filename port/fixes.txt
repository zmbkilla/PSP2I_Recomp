# Instruction fixes applied by allegrexrecomp emit --fixes, each a genuine bug
# in the original game. A fix must not change control flow.

# 0x08A937B4: phase accumulator step. The function advances a 16-bit phase at
# +0x98 by trunc(step(+0xC0) * scale) every frame. The original computes
# scale = fps / 30 (div.s $f1, $f1, $f0 with $f1 = fps, $f0 = 30.0), which is
# the factor for converting a DURATION in 30 Hz ticks to frames; for a
# per-frame STEP the factor is 30 / fps -- the engine's own frame-step value
# (timing state +0x18 = 30 / fps, set in 0x08B81830). At 30 fps both are 1.0,
# so the original behaviour is unchanged; at 60 fps the original runs the
# phase at 4x speed (2x per frame, 2x the frames), and at the game's own
# 20 fps mode at 0.44x. The PPSSPP 60 FPS cheat swaps the operands the same way.
0x08A937B4 0x46010043   # div.s $f1, $f0, $f1   (30 / fps)

# 0x08A5C27C: NPC walk-to-point arrival check (0x08A5BBF0 walks an NPC to a
# point: turn toward it, step forward, stop once arrived). "Arrived" is a
# horizontal distance under 30/fps -- one frame's walk at the fast speed, so
# the radius halves at 60 fps (1.0 -> 0.5). Walking (12/fps per frame) and
# turning (0x24000/fps per frame) are both fps-scaled, so the NPC's turning
# circle is 12 / 14.1 rad/s = 0.85 at any frame rate: inside the 30 fps
# radius, outside the 60 fps one, and the NPC circles the point forever
# instead of arriving -- Rapico spinning on the spot in his shop, Hyuga
# turning past the player. Logged at 60 fps: the walk restarted its turn every
# frame with the target held ~90 deg to the side (circling) for the whole
# recording. The radius keeps its 30 fps size: both loads now take the 30.0
# constant the next instructions already use (0x08E011D8), so 30 / 30 = 1.0.
0x08A5C27C 0x3C0208E0   # lui $v0, 0x08EE  ->  lui $v0, 0x08E0
0x08A5C280 0xC44011D8   # lwc1 $f0, fps    ->  lwc1 $f0, 30.0   (arrival radius 30/30)
